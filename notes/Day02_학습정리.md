## Chapter 1. 생성형 LLM 기본개념

### LLM이란

**필요성**: LLM은 "정답을 검색"하는 게 아니라 "가능한 답을 확률적으로 생성"하는 모델이다. 이 차이를 모르면 왜 같은 질문에 답이 매번 조금씩 달라지는지, 왜 Hallucination이 생기는지를 이해할 수 없다.

- 대규모 텍스트(웹 문서·논문·코드 등)를 사전학습해 언어 이해·생성 능력을 갖춘 기초 모델(foundation model)
- 최신 흐름: 단순 챗봇 → 업무 자동화형 AI Agent, 텍스트 중심 → 멀티모달, 클라우드 모델 → 경량화·온디바이스 모델

**LLM 학습의 3단계**

| 단계 | 하는 일 | 비유 |
|---|---|---|
| ① Pretraining (사전학습) | 대규모 텍스트로 언어·지식 자체를 학습 | 책을 엄청 많이 읽기 |
| ② Instruction Tuning | "지시를 잘 따르도록" 추가 학습 | 지시 알아듣는 훈련 |
| ③ Task-specific Fine-tuning | 특정 작업(감성분석 등)에 맞춰 미세조정 | 특정 업무 전문 교육 |

### 확률적 생성 vs 결정적 선택

**필요성**: 이 개념을 알아야 "같은 프롬프트를 여러 번 넣었는데 답이 다르다"는 현상을 버그가 아니라 정상 동작으로 이해할 수 있다.

```
입력: "오늘 날씨가 정말..."
좋다 55% / 덥다 20% / 춥다 15% / 흐리다 10%
```
- **결정적 선택**: 항상 확률 1등만 골라서 → 같은 입력엔 항상 같은 답 (일관성↑)
- **확률적 선택**: 확률 분포를 따라 무작위로 고름 → 같은 입력에도 답이 달라질 수 있음 (다양성↑)

### LLM 발전사 (압축 요약)

```
RNN/LSTM (한 단어씩 순서대로 읽음, 느림)
→ Attention (중요한 단어만 골라 보기)
→ Transformer (2017, 모든 단어를 동시에 봄 — 지금 모든 LLM의 기반)
→ GPT/BERT (대규모 사전학습)
→ ChatGPT (대화형, 사람 피드백으로 다듬음)
→ 지금: 추론 모델 + AI Agent 시대
```

**ChatGPT가 자연스러운 이유**
```
기존 GPT (다음 단어 예측만)
→ Instruction Tuning (지시 따르는 훈련 추가)
→ RLHF (사람이 더 좋은 답을 선택 → 그 피드백으로 재학습)
```

> Transformer 내부의 세부 수식(Q/K/V, Self-Attention 계산)은 딥러닝 연구자가 아니면 실무에서 직접 만질 일이 거의 없어서, "동시에 여러 단어를 보는 구조"라는 정도만 알면 충분하다.

### LLM의 한계

**필요성**: 한계를 모르고 LLM을 쓰면 잘못된 정보를 그대로 신뢰하게 된다. 이 한계를 아는 것 자체가 Day03 RAG, Day02 프롬프트 지침 설계의 출발점이다.

1. **Hallucination(환각)**: 그럴듯하지만 틀린 답을 만들어냄 → RAG, 출처 검증으로 완화 (Day03에서 다룸)
2. **Bias(편향)**: 학습 데이터의 편향이 답변에 전이됨 (성별·인종·언어별 정확도 차이 등)

## Chapter 2. 프롬프트·컨텍스트 엔지니어링

### 프롬프트 엔지니어링 — R-T-C-F 공식

**필요성**: 같은 질문이라도 역할·맥락·형식을 명시하지 않으면 LLM은 뻔한 일반론만 내놓는다. "어떻게 물어보는가"가 답의 품질을 결정한다.

**좋은 프롬프트 = 역할(Role) + 목표(Task) + 맥락(Context) + 출력형식(Format)**

| 요소 | 질문 | 예시 |
|---|---|---|
| Role | 누구 관점으로? | "너는 VOC 분석 담당자다" |
| Task | 뭘 해결해야 하나? | "고객 불만을 유형별로 분류해줘" |
| Context/Audience | 누구를 위한 답인가? | "대상은 신축 아파트 입주 고객" |
| Format | 어떤 형태로? | "표로 정리, 우선순위 Top 3" |

```
나쁨: "빌트인 오븐 설명해줘" → 뻔한 일반론만 나옴
좋음: 역할 + 대상 고객 + 조건(디자인/성능/스마트기능 관점) + 출력형식(표+슬로건) 지정
→ 훨씬 쓸모있는 답 나옴
```

**Zero-shot vs Few-shot**
- Zero-shot : 예시 없이 지시만 → "감정을 분류하세요"
- Few-shot : 예시 2~3개 보여주고 패턴 따라하게 함 → 정확도 훨씬 상승 (Day03 LangChain에서 실습)

### 컨텍스트 엔지니어링 — "무엇을 알려줄지" 설계

**필요성**: 프롬프트가 "어떻게 물어볼지"라면, 컨텍스트는 "답하는 데 필요한 자료를 미리 챙겨주는 것"이다. 아무리 프롬프트를 잘 써도, 참고할 자료가 없으면 LLM은 일반론밖에 답할 수 없다.

```
컨텍스트 없이: "식기세척기 고객 불만을 분석해줘" → 뻔한 일반론
컨텍스트 있이: VOC 1,200건 + 모델별 비율 + AS이력 + 매뉴얼까지 제공
→ 실제 데이터 기반의 구체적 분석 가능
```

| | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 |
|---|---|---|
| 핵심 질문 | 어떻게 물어볼 것인가? | 무엇을 알려줄 것인가? |
| 실패 원인 | 지시가 불명확 | 필요한 정보 부족/잘못됨 |

**컨텍스트 엔지니어링 핵심 기술 4가지**
- **RAG** : 질문과 관련된 문서를 검색해서 같이 넣어주기 → Day03에서 배움
- **메모리** : 이전 대화·사용자 선호를 기억 → Day04 LangGraph State에서 배움
- **Tool Calling** : LLM이 직접 DB 조회·계산 등 도구 실행 → Day01에서 원리를 다룸
- **Context Window 관리** : 필요한 자료만 골라 넣기 (관련성 높은 것 우선, 중복 제거)
